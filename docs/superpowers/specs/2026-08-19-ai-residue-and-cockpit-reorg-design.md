# AI residue removal + interactive Cockpit reorganization — design

**Date:** 2026-08-19
**Status:** approved in chat 2026-08-19, pending spec review

## Goal

Two related gaps identified while reviewing the base premise of YCF ("organize folders so
errors are easy to locate, a third party can understand the project, it looks
professional, and it's free of useless residue an AI assistant leaves behind"):

1. `ycf ai-residue` today only *detects* AI/dev residue; it cannot apply anything.
   `ycf cleanup` already proves the safe-apply pattern (checkpoint -> apply -> verify ->
   auto-rollback on failure) for a different, narrower rule set. Extend detection to catch
   more of what assistants like Claude/Codex leave behind, and let the mechanically-safe
   subset apply through the same pattern.
2. Folder reorganization decisions (which live in
   `skills/ycf-quality-gate/references/stack-profiles.md`, read by an AI agent, never by
   the deterministic core) are proposed only as prose in a chat session today. Give that
   proposal a durable, visual home in the Fuck-O-Meter/Cockpit dashboard, with a real
   one-click apply per move, an undo, a way to mark a move permanent, and an end-of-session
   comparison + optional GitHub push -- without moving architecture-decision judgment into
   the deterministic core, which the project's own constraints explicitly forbid (no LLM
   calls, no invented decisions in `packages/core`).

## Non-goals

- The core engine still never decides *where* a file should go. That judgment stays with
  the AI agent (via the `ycf-quality-gate` skill), exactly as today -- this design only
  gives an already-agent-approved plan a place to be reviewed and executed with one click.
- No change to the read-only nature of `/plan/*` endpoints or to any existing command's
  default behavior. Every new write path requires an explicit action (click or `--yes`)
  exactly like `cleanup` does today.
- `--yes` on `ai-residue` never deletes a whole file, never renames anything, and never
  touches `suspicious-filename`, `mystery-helper`, `todo-from-hell`, or the redundant-comment
  category (see below) -- those stay report-only.

## Part A -- `ycf ai-residue --yes` (bounded; implemented via normal TDD workflow, no plan doc needed)

**Detection widens, auto-apply does not.** Three categories, three different treatments:

| Category | Detection | `--yes` deletes it? |
|---|---|---|
| Existing markers (`temporary fix`, `final-final`, `backup copy`, `todo: remove`) | comment-line regex (already exists) | **Yes** (already safe today, unchanged) |
| New: assistant meta/placeholder comments (`// Generated by AI`, `// As an AI language model...`, `// Added by Claude/Codex to...`, and similar first-person/meta phrasing an assistant leaves about its own edit) | new comment-line regex, same shape as the existing one | **Yes** -- still always a pure comment line, zero behavior change |
| New: wider generic-name list for `mystery-helper` (extend the existing `processDataThing|doThing|helper|mysteryHelper|handleStuff` alternation with more assistant-typical generic names) | regex extension to the existing rule | No -- unchanged, stays `report-only`, renaming is judgment |
| New: comments that only restate the line below them (classic AI tic, e.g. `// increment i by 1` over `i++`) | new heuristic (compare comment tokens against the very next non-comment line's tokens) | No -- flagged as a **new** `report-only` finding for review; too fuzzy to auto-delete safely, real risk of false positives |

Implementation shape (mirrors `cleanupDevArtifacts` exactly):

- `packages/core/src/index.ts`: extend the `ai-residue` regex to the new marker phrasing;
  extend the `mystery-helper` name alternation; add a new `redundant-comment` rule
  (`report-only`, new `ruleId`) using the next-line heuristic.
- New `cleanupAiResidueMarkers(target)` in core, parallel to `cleanupDevArtifacts`, which
  removes only lines matched by the (now-widened) `ai-residue` ruleId -- nothing else.
- CLI: `ycf ai-residue` gains `--dry-run` (default behavior, explicit flag) and `--yes`
  (checkpoint -> `cleanupAiResidueMarkers` -> `verify()` -> rollback on failure), following
  `cleanup`'s existing command body almost line for line.
- Tests: one fixture per new regex category (true positive), one adversarial fixture per
  category proving it does *not* fire on legitimate comments/names, and one `--yes`
  end-to-end test proving `mystery-helper`/`redundant-comment`/`suspicious-filename`
  findings survive untouched after `--yes` while `ai-residue` findings are gone.

## Part B -- Interactive reorganization panel in the Cockpit (architectural)

### Lifecycle

1. **Propose (chat, unchanged):** an AI agent runs `ycf understand`, reads
   `stack-profiles.md`, proposes old-path -> new-path moves, and only after the user
   approves them in chat, writes them out as a plan file (see format below).
2. **Review (Cockpit, new):** `ycf cockpit` shows every proposed move as its own row/card:
   old path, new path, one-line reason, and a status badge (`PENDING`, `APPLIED`,
   `ROLLED_BACK`, `KEPT`).
3. **Apply (Cockpit, new, one click):** runs the move through the existing engine, verifies,
   and either lands on `APPLIED` (with Undo/Keep) or auto-rolls-back on verification failure
   (with the failure reason shown inline) -- no user decision needed on failure, matching
   `cleanup`'s existing behavior.
4. **Undo / Keep (Cockpit, new, one click each):** reverse a specific applied move, or
   dismiss its undo option.
5. **Finish (Cockpit, new):** once every row is in a terminal state (`APPLIED`/`KEPT`/
   `ROLLED_BACK`), a "Finalizar" action shows the before/after comparison and asks whether
   to commit (and optionally push) or leave everything uncommitted locally.

### Plan file format (reuses existing types, no new schema)

Written by the agent to `.ycf/reorganization-plan.json`, typed exactly as the existing
`ArchitecturalRefactorPlan` (`packages/core/src/refactor-types.ts`) -- one `RefactorBlock`
per proposed move, `mode: 'SUPERVISED'`, `operations: [{ kind: 'MOVE', source, destination,
updateImports: true }]`, `reason` holding the plain-language justification the agent already
produces in chat today. No new TypeScript types are introduced for the plan itself.

### New Cockpit server surface (`packages/core/src/cockpit.ts`)

All of it stays bound to `127.0.0.1` and gated by the same per-session random token as
every existing route. The file's current top-of-function comment ("there is no apply/
execute/write endpoint here or anywhere reachable from it") gets rewritten to describe the
new, narrower guarantee honestly: *no endpoint invents a move -- every write endpoint only
ever executes a move that already exists, verbatim, in a plan file an agent wrote after
the user approved it in chat.*

- `GET /plan/reorganization` -- serves `.ycf/reorganization-plan.json` if present, `404`
  with a clear "no plan yet" body otherwise. Read-only, same pattern as the three existing
  `/plan/*` routes.
- `POST /apply/move` `{ blockId }` -- looks up the block in the plan file, runs
  `applyRefactorOperation` for its one operation, then a **fast** verification pass
  (lint + typecheck only, reusing the same FAST-check filtering `runVerification` already
  does internally in `refactor-executor.ts` -- export or duplicate that helper rather than
  running the full lint/typecheck/test/build suite on every single click, which would make
  a 20-move session unusably slow). On failure: calls the operation's `undo()` immediately,
  responds with the failure reason, block stays `PENDING`. On success: keeps the
  `AppliedOperation` (including its `undo` closure) in an in-memory
  `Map<blockId, AppliedOperation>` scoped to this server instance, responds `APPLIED`.
  A full verification run happens once, at `/finalize`, not per move.

  **Deliberately does not call `executeRefactorPlan`.** That function is a correct fit for
  batch/unattended runs, but on success it discards the `AppliedOperation[]` (and therefore
  every `undo` closure) before returning -- its `RefactorExecutionReport` is JSON-serializable
  by design, so it cannot carry live closures back to the caller. The Undo button needs
  exactly the closure `executeRefactorPlan` throws away, so this is a small, new, dedicated
  function (`applyReorganizationMove(target, block)` in `refactor-operations.ts` or a new
  module), not a wrapper around the batch executor. It also skips
  `beginCheckpointJournal`/the persistent git-ref checkpoint journal entirely -- that journal
  exists for crash-recovery mid-batch-run, and (see below) its per-block "before" ref isn't
  actually usable for surgical single-move undo here anyway, so there is nothing to gain by
  writing to it.

  *Why not the persisted git-ref journal for Undo:* `updateBlockCheckpoint` snapshots
  whatever `HEAD` is at the moment a block starts running. Because YCF never commits on the
  user's behalf between applied moves, `HEAD` does not move between clicks -- every move's
  "before" ref would point at the same original commit. Resetting to it would discard every
  other already-applied move sitting uncommitted in the working tree alongside it, not just
  the one being undone. Only the operation's own in-memory `undo()` (a targeted, file-level
  reverse of just that move) does the right thing, which is why the limitation below is
  real and worth stating plainly rather than working around.
- `POST /undo/move` `{ blockId }` -- calls the cached `AppliedOperation.undo()`, removes it
  from the map, responds `PENDING`.
- `POST /keep/move` `{ blockId }` -- drops the cached entry from the map without calling
  `undo()`, responds `KEPT`. No git action -- YCF still never commits on your behalf.
- `POST /finalize` -- computes `architectureDiff` (already built) and a before/after
  `audit().score.fucked` comparison across every block touched this session, writes
  `.ycf/reorganization-report.md` (same pattern as `writeUnfuckReport`/
  `writeRefactorExecutionReport`), and returns the summary for display. Does **not** touch
  git by itself.
- `POST /finalize/publish` `{ push: boolean }` -- only reachable after `/finalize`. Stages
  **only the files this session actually changed** (the union of every applied block's
  `changedFiles`, tracked already in the in-memory map) with explicit `git add <path>...`
  calls, then commits -- never `git add -A` / `git commit -a`. This matters: a user can
  open `ycf cockpit` while other, unrelated work is already sitting uncommitted in the same
  repo, and a blanket stage-everything would silently sweep that in. If `push` is true,
  pushes to the current branch's upstream. Requires a second explicit confirmation
  client-side before this call is ever made (see UI below). If there is no configured
  remote/upstream, responds with a clear error and the commit still stands locally -- never
  silently fails or retries.

### Explicit, stated limitation (surfaced in the UI, not hidden)

Undo/Keep only work while the same `ycf cockpit` server process that applied the move is
still running -- the `AppliedOperation.undo` closures are in-memory, not persisted. If the
terminal is closed and Cockpit reopened later, previously-`APPLIED` rows show as applied
with no Undo button and a one-line note: "Undo is unavailable after restarting Cockpit --
the change is already in your working tree, uncommitted; use git directly if you want to
revert it." This mirrors the honesty standard already set for the Mac packaging disclaimer
and the "static evidence" notes elsewhere in the product.

### UI panel (Fuck-O-Meter dashboard, new tab: "Reorganize")

Text/table based, consistent with the existing dark theme and tab structure in
`cockpitHtml`. One row per block:

```
📦 src/legacy/greeting.mjs → src/features/salutation.mjs
   Reason: features/ already exists, grouped with the rest
   [ Apply ]

✅ src/legacy/helper.mjs → src/lib/format-total.mjs        APPLIED
   [ Undo ]   [ Keep permanently ]
```

A sticky footer bar becomes active once every row is terminal:

```
7 applied · 0 rolled back            [ Finalize ]
```

Clicking Finalize shows the score/architecture comparison inline, then:

```
Save changes locally only   /   Commit and push to GitHub
```

Choosing push shows one more explicit confirmation ("This pushes to <remote>/<branch>.
Continue?") before `/finalize/publish` is ever called.

If `.ycf/reorganization-plan.json` does not exist, the "Reorganize" tab shows a short
explanation instead of an empty table: "No reorganization plan yet -- ask your AI agent to
propose one after reviewing your project's structure."

### Testing

- Core: unit tests for the four new endpoints (`apply`/`undo`/`keep`/`finalize`/
  `finalize/publish`) covering success, verification failure + auto-rollback, undo after a
  successful apply, keep, finalize with no plan file, and publish with no configured
  remote.
- Core: a test proving the in-memory map is per-server-instance (a fresh
  `startCockpitServer` call has no memory of a previous instance's applied moves).
- CLI/manual: one smoke pass through `ycf cockpit` with a hand-written
  `reorganization-plan.json` fixture, clicking through the full lifecycle in a real browser
  session, since the existing acceptance-demo script exercises the engine but not this new
  HTTP surface end to end.

## Open risk carried forward, not resolved here

`POST /finalize/publish` with `push: true` is the first place YCF's Cockpit server ever
performs a Git operation with an external side effect (pushing to a shared remote). It is
scoped as tightly as this design can make it (opt-in, double-confirmed, loopback-only,
token-gated, only reachable after every move is already terminal) -- but it is a real
philosophy shift from "YCF never commits for you," worth flagging explicitly rather than
burying in the implementation.
